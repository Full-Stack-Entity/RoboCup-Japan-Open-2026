# 阶段 3：导航闭环

本阶段不在 C++ 中硬编码地图坐标。房间区域、房间搜索点和目的地候选位姿全部来自阶段 2 生成的四套 `config/environments/layout_*.yaml`。比赛当天重新导入地图后，导航代码无需修改。

## 1. 编译和自动测试

```bash
cd ~/RoboCup-Japan-Open-2026
source /opt/ros/humble/setup.bash
colcon build --packages-select handyman_rebuild_ros2 --symlink-install
source install/setup.bash
colcon test --packages-select handyman_rebuild_ros2
colcon test-result --verbose
```

测试覆盖四套地图的 Nav2 读取、房间区域与候选点、最近候选选择、失败后切换候选、TF 房间验证，以及原有协议回归。导航集成测试使用假的 Nav2 action server，不需要 Unity，也不需要等待六个 session。

## 2. 启动前检查

每次只能运行一套同名 Nav2 节点。先在之前打开地图或 Nav2 的终端按 `Ctrl+C`，再检查：

```bash
source /opt/ros/humble/setup.bash
source ~/RoboCup-Japan-Open-2026/install/setup.bash
ros2 node list
```

如果仍出现 `/map_server`、`/amcl`、`/controller_server`、`/planner_server` 或 `/bt_navigator`，说明旧进程仍在运行。不要同时启动新布局，否则新 AMCL 可能收到旧地图。

## 3. 启动指定布局

先启动 Windows 上对应的 Unity session，再在 Ubuntu 运行：

```bash
cd ~/RoboCup-Japan-Open-2026
source /opt/ros/humble/setup.bash
source install/setup.bash
ros2 launch handyman_rebuild_ros2 phase3_navigation.launch.py layout:=LayoutA
```

将 `LayoutA` 替换为 `LayoutB`、`LayoutC` 或 `LayoutD`。该命令同时启动当前地图、AMCL、Nav2、两个 Unity 通信桥和 Coordinator。

仅检查 ROS 端、不连接 Unity 时：

```bash
ros2 launch handyman_rebuild_ros2 phase3_navigation.launch.py \
  layout:=LayoutA start_bridges:=false
```

## 4. 启动后检查

另开 Ubuntu 终端：

```bash
source /opt/ros/humble/setup.bash
source ~/RoboCup-Japan-Open-2026/install/setup.bash
ros2 lifecycle get /map_server
ros2 lifecycle get /amcl
ros2 action list | grep navigate_to_pose
ros2 run tf2_ros tf2_echo map base_footprint
```

正确结果应为 `map_server` 和 `amcl` 均为 `active`，存在 `/navigate_to_pose`，且 `tf2_echo` 持续输出位置。RViz 的 Fixed Frame 使用 `map`，建议显示 Map、TF、LaserScan、Global Costmap 和 Local Costmap。

统一 launch 会从当前布局 YAML 自动设置 AMCL 的 `initial_pose.x`、`initial_pose.y` 和 `initial_pose.yaw`，不需要在 RViz 中手工点击 `2D Pose Estimate`。

## 5. 指令触发后的闭环

Coordinator 收到 `Environment`、`Are_you_ready?` 和 `Instruction` 后会：

1. 从当前布局 YAML 读取目标房间候选点；
2. 若机器人已在房间内则跳过移动；
3. 否则向 `/navigate_to_pose` 发送候选目标；
4. 单次超时后取消目标；
5. 失败时清理全局与局部代价地图，再尝试下一个候选；
6. Nav2 成功后通过 `map -> base_footprint` TF 和房间多边形再次验证；
7. 验证成功后才发送 `Room_reached`；
8. 尝试耗尽后发送 `Give_up`，不会伪造成功。

如果 Nav2 action 已出现但生命周期仍在启动，目标可能被临时拒绝。执行器会在服务器准备窗口内重发同一候选点，不会把这种启动竞态计入三次导航尝试。

目的地导航使用同一执行器，候选按 `destination` 和 `destination_room` 筛选，并额外验证机器人与候选位姿的距离。后续抓取阶段完成后可从 `kNavigatingToDestination` 状态直接调用。

## 6. 参数和常见错误

默认导航尝试次数和超时来自 `config/recovery.yaml`，可用 ROS 参数覆盖：

```bash
ros2 run handyman_rebuild_ros2 handyman_coordinator --ros-args \
  -p navigation.maximum_attempts:=3 \
  -p navigation.goal_timeout_sec:=60.0 \
  -p navigation.server_wait_timeout_sec:=15.0 \
  -p navigation.room_boundary_tolerance_m:=0.20 \
  -p navigation.destination_tolerance_m:=0.75
```

- `Nav2 action server was not available`：Nav2 未启动或生命周期未激活；
- `robot pose was unavailable`：缺少 `map -> odom -> base_footprint` TF；
- `outside the expected room`：地图坐标、AMCL 定位或房间区域有偏差；
- 机器人不动：检查 `/hsrb/base_scan`、`/odom`、`/hsrb/command_velocity` 和 Unity 桥；
- 地图不符：通常是旧 `map_server` 尚未退出。

## 7. Unity session 测试安排

日常开发无需逐 session 监听。自动测试覆盖协议、候选切换和恢复，RViz 可脱离 Unity 查看静态地图。最终动态验收时，每个布局分别测试一个远房间、一个跨门房间、一个目的地候选和一次人为阻挡恢复即可；记录结果后等待下一 session，不必为普通代码修改从 session 1 重跑。
