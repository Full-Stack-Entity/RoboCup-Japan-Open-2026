# 搜索运行器与故障验证

2026-09-17。本文对应 `search_session_runtime.py`，不是完整比赛启动说明。

最终版本离线验收通过：273 项 Python 单元测试、7 组 C++/ROS 回归、默认禁用
检查及下表 16 个场景；另通过原有真实 worker 路线中间点取消/退役兼容性检查。
各场景核对持久化记录、终态与子进程清理。历史测试保留不覆盖；真实 Unity
和模型准确率仍未在这些离线测试中验收。

## 完成的接入

运行器把任务请求、实时地图校验、导航 worker、只读视觉观察器和进程监督接在一起。
默认禁用，未给 `--execute` 不创建 ROS 节点，也不启动子进程。
离线执行限定 ROS domain 73 / localhost / 测试 Nav2 action；其他环境还需要显式
`--allow-live`。这个开关不是实机验收证明，目前不要替换比赛启动脚本。

每轮只选择指定房间内的一个已配置搜索点（默认索引 0）。地图验证通过后先启动
观察器，确认它已订阅，再启动 worker。目标绑定任务、搜索点和地图摘要。
worker 生成实际 ROS action UUID 后先提交派发意图；监督端将编号、任务、地图
摘要、位姿、用途和 action 地址写入 SQLite 并完成同步提交，才回复确认。
只有收到与原始意图完全匹配的确认，并在放行时重新通过地图/租约检查，原请求
才会发送给 Nav2，不生成第二个编号。
所有搜索路线中间点、最终搜索点和重试均经过该拦截点。
观察器要求对应导航终态、稳定 TF 和新鲜 RGBD 证据；不能拿旧任务结果继续执行。

观察结束后，运行器请求协调器发起取消；只有观察器合法结束、已知目标有终态、
worker 完成匹配取消编号的退役握手并退出 0，才向外报告 `cancel_drained`。
此后才发布内部 `search_observation` 结果，允许下一轮进入。
结果中的三维点为 `odom` 坐标，仍为 `actionable: false`，不直接驱动抓取。

发现故障后锁定运行器，停止续发 worker 租约，并独立撤销已登记的精确目标编号。
这一步不依赖协调器回复。故障不会因迟到成功消息自动解除；不发送
`Task_finished`、`Object_grasped` 或 `Does_not_exist`。

属于当时版本，不应拿旧程序绕过本轮保护。失败和中间运行记录均保留不覆盖。
每个场景还检查 `cleanup.json`，要求运行器
退出 0、无需强杀运行器、没有遗留的观察器/worker 子进程。
重启故障用例有意 SIGKILL 旧运行器及其子进程；这里的退出 0 指恢复运行器的
最终退出。故障注入本身单独记录，不能误解为所有进程一直正常退出。
路线中间点补充证据在同目录 `waypoint-compatibility`。

| 场景 | 检查重点 |
| --- | --- |
| sequence | 两轮自动启动/清理；第二轮注入旧取消消息仍正常完成 |
| no_target | 单视点无目标只返回 incomplete，不宣告不存在 |
| cancel | 中途取消后导航撤销，观察器和 worker 正常退役，无目标结果 |
| runtime_shutdown | 活动任务中 Ctrl+C，先撤销和清理子进程，最后关闭 ROS 上下文 |
| observer_crash | 观察器崩溃，撤销导航并保持锁定 |
| observer_crash_orphan | 协调器已退出，观察器随后崩溃，仍能独立撤销已登记目标 |
| worker_crash | 已登记后 worker 崩溃，由监督端撤销目标 |
| worker_crash_early | 不等待接受登记即杀死 worker，仍按预先记录的编号撤销 |
| map_change | 实时地图变化，撤销导航并保持锁定 |
| before_send | 丢弃确认、发送前杀死 worker；Nav2 收到 0 个目标 |
| delayed_accept | SendGoal 已收到但接受回复延迟时杀死 worker；之后仍撤销同一编号 |
| accepted_lost | 丢弃接受登记消息并杀死 worker；依靠预先持久化编号撤销 |
| recovery | 强杀运行器及子进程，沿用原日志启动恢复，撤销旧目标且不派发新目标 |
| recovery_unknown | 已记录但未发送的目标恢复为 UNKNOWN，保留记录并保持锁定 |
| reject_once | Nav2 首次拒绝，拒绝证据落盘后正常重试，新旧编号分别核算 |
| journal_write_failure | 写事务被阻塞，落盘失败不确认、不发送目标 |

## 持久化日志与恢复规则

执行运行器现在必须显式提供 `--journal`；不要将日志跟每次新建的观察输出目录
一起更换。建议未来 Unity 联调使用固定的 Ubuntu 本地文件，例如：

```text
--journal /home/crazylearner/.local/state/handyman/search-dispatch.sqlite3
```

这只是日志路径示例，不是启动 Unity 控制的命令。不要使用移动盘、Windows
挂载盘或网络共享来存放这份恢复依据。现有测试为每个独立场景建库，恢复场景
明确复用同一数据库，不会污染正式日志。

- 同一日志只允许一个运行器持有锁；写入失败、内容校验失败或锁冲突不放行。
- 重启发现未结束记录时，只对记录中的精确 UUID 查询/撤销，不重发导航任务。
- 每次运行使用新的内部通信命名空间；即使任务编号相同，旧 worker 也无法从新
  运行器获得续租或派发确认。命名空间隔离不是 ROS 消息认证机制。
- Nav2 的 UNKNOWN、服务不可用、取消请求被拒绝都不是终态证明，记录不清除。
- 已确认的 SUCCEEDED/CANCELED/ABORTED 终态会落盘。只有 worker 明确收到拒绝
  或在本地拦截阶段确定没有发送时，才可使用单独的拒绝证明；不能由 UNKNOWN 推出。
- 恢复进程即使收齐终态也保持派发锁定，不自动继续比赛。应先核实旧进程已停止、
  机器人实际状态与恢复日志，再重新启动协调器/运行器；未确认记录不能手工删掉。
- 保留数据库及其 SQLite 事务文件，运行期间不复制覆盖、删除或修改；更换空日志
  以绕过锁定会使保护失效。日志不是模型训练数据，不能随数据集清理。

## 必须保留的限制

1. 原来的“已经发送但监督端不知道编号”窗口已由搜索保护器的发送前持久化确认
   流程处理；其保证以保留且可靠的日志、当前 ROS Humble 拦截接口和可信 Nav2
   回应为前提。它不保证任意断网、磁盘毁损或 Nav2 重启丢失记录后仍能撤销；
   无法确认时保持锁定。第三阶段普通房间/目的地导航不因此自动具有持久化恢复。
2. `cancel_drained` 是软件动作和进程清理证据，不是 Unity 机器人实际静止证明。
   未完成真实 Unity/Nav2、图像断流、暂停/恢复等联调验收；本轮没有恢复 Unity。
3. 运行器尚未覆盖整房间多视点扫描，也不启动 YOLO/RGBD 推理服务；本测试中的
   检测是构造数据，不能证明模型识别准确率。现有真实视觉诊断服务需要另行接入。
4. 单点看不到目标、临时行人阻挡或导航故障均不能直接推出不存在。整房间搜索
   覆盖证据以及静态不连通政策仍需在完整任务流程中接入验收。
5. 结果还未推进比赛抓取/放置状态机；本模块不是阶段 4 全部完成，更不是阶段 5。
6. 本轮增加了搜索派发日志和重启恢复，但没有 ROS 发布者身份认证；配置文件与 C++ 端
   使用同一份目录，但尚无贯穿两端的环境配置摘要绑定。不要在线改地图/配置。
